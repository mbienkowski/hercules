skills / code-of-conduct-generator

Three kinds of evidence, one gate that refuses all of them equally

The generator writes a project's engineering standards by measuring the repository, asking its owner, and reading its code. What makes the output trustworthy is not that a model wrote it carefully — it is that every rule must name evidence the run actually carries, and two programs refuse the draft when it cannot.

It runs against any repository, in any language. The tools are stdlib Python, shipped to every ecosystem; they read and never write. Only the last step writes, and only the code-of-conduct file itself.

The pipeline

Evidence enters by three lanes and leaves as one JSON envelope. Nothing reaches the document that has not passed the envelope gate first.

The run, step by step

Ten steps, in this order. A content test pins the order, so the shipped prose cannot drift out of sequence.

01
Plan mode, and pick a depth
Nothing is scanned before the user has seen the flow. Quick for a small repository; Thorough adds the gap pass and an advisor review.
02
Find any existing code-of-conduct
One match means update mode, and update mode is additions-only. Several matches are never silently resolved — it asks.
03
Scan, then read what the scan cannot know
The tool reports what the repository declares, how its history reads, which directories are alive, and which grow by one-more-of-a-kind. It knows no language — everything language-shaped is the agent's to read, recorded as observations.
→ facts · liveness · unknowns · observations
3b
Write an extractor; let the tool run it
The agent writes a small read-only extractor for the language in front of it — the one function a language appears in — and coc_scan.py extract runs it under a wall-clock bound, kills anything it spawned, caps what it may print, and holds every path it reports against HEAD. A timeout fails loud: one narrowed retry, then stop and report.
→ areas · edges · chokepoints · entrypoints · conventions · files_processed / files_at_head
04
Ask, in one batch
Never fewer than five questions, never trickled. Every split convention the extractor found becomes one question carrying both sides' counts — recent work says where a team is going and equally where it is retreating from, and no count can tell those apart.
→ answers
05
Draft from all three streams
Orientation, then themed sections whose concerns each get a sub-heading and a summary. Rules group under one tier header per posture as a numbered run, and a directive takes the lines it needs.
→ never past 8 directives under one heading · split at the first clear boundary
06
Gap pass and critical review
A coverage map runs once as a gap detector — each load-bearing omission becomes a chat recommendation, never a silent addition. Then an advisor reviews the draft and returns findings only.
07
Gate, then present
The envelope goes to coc_gate; the laid-out markdown goes to coc_lint. Exit 0 ships. Any other exit gets fixed, never argued past.
08
Approve and write
Written atomically. The generator never creates or edits any file besides the code-of-conduct itself — a reference line for the instructions file is offered in chat, and adding it is the user's edit. Then the linter runs again, against disk.
09
Review and commit
Exactly that one path is staged and committed, so other staged work is never swept in. A push is offered, never taken.

The three tools

Capability is declared, not assumed — a hygiene scan holds each tool to its row, and a tool with no row fails the scan rather than passing quietly. All three answer with one JSON object on every path, including refusals.

ToolPostureReachesRefuses
coc_scan.py Fails closed; opens no repository file — asks git, and runs the extractor bounded git ls-files, ls-tree, log, tag, rev-parse; spawns the agent's extractor under a deadline, its own session killed whole, stdout read through a 1 MB cap. Read-only and no-network stay blueprint instructions — there is no sandbox behind them An unreadable repository; an artifact whose shape breaks, whose paths miss HEAD, or whose counters are impossible; a hung or flooding extractor — loud, with one narrowed retry
coc_gate.py Pure function, fails closed Nothing. No path is opened, no subprocess runs A rule untagged, uncheckable, uncited, duplicated, over-grouped, or past the hard ceiling
coc_lint.py Reports, never edits git ls-files, ls-tree — a cited path resolves by membership, never by touching disk A broken shape, a dangling citation, a literal that will rot, an unverifiable claim
Why membership, not the filesystem. A code-of-conduct written by someone else is untrusted text. Resolving its paths against the repository's own file list means a document can never be used to ask what exists outside the repository.

## Why this is the way it is       ← every reason, last
The first sentence is the rule. It has to read alone, because that is the line a skimming reader takes away. Everything after it — what the rule prevents, the case it generalises to, the check, the fragment — is there for the reader who stopped.

What each gate refuses, and why it exists

Every rule below was added because a real defect got through without it. That is the reason to keep them: each one is a bug that already happened once.

FindingWhereThe defect it exists to prevent
rule_untaggedgateA rule whose enforcement weight the reader cannot tell — everything reads as equally optional.
rule_uncheckablegateA rule no reviewer can settle objectively, so compliance becomes a matter of taste.
rule_uncitedgateA rule nobody can trace to a scan observation, a user answer, or a reading of the code.
citation_unknowngateAn id nothing produced — the shape of a rule invented first and justified afterwards.
observation_path_escapesgateEvidence claimed from outside the repository, which says nothing about it.
group_oversizedgate lintMore rules under one heading than a reader can hold, so nobody can say what lives where.
orientation_missinglintA file that opens cold with rules and orients nobody.
group_unsummarizedlintRules with no statement of intent, so they are obeyed literally and generalised wrongly.
directive_untieredlintA requirement with no posture — is it blocking, or a preference?
why_missing / why_misplacedlintReasons scattered through the rules, or absent, leaving nothing to reason from.
snapshot_literallint"17 files today", "10 of 10", a pinned version — true when written, false a week later, and nothing would ever say so.
unhedged_universallint"the only X anywhere", "on every host". A path check proves existence and can never prove an absence, so these clear every gate while being false. Blind review found this the single largest source of wrong statements.
check_unfalsifiablelintA Check: that names nothing runnable — prose in the position that promises verification.
family_uncoveredlintA directory the repository grows by that the document never names, leaving the next contributor to guess a whole extension path.
citation_danglinglintA path the repository no longer has — a rule pointing at something somebody moved.
path_not_at_headextractAn extractor naming a file nobody can open reported something else too — the whole artifact is suspect.
counters_impossibleextractMore files read than found, or found than tracked. An artifact that read a fifth of the repository is otherwise shaped exactly like one that read all of it.

How it stays universal

Four layers, and none of the shipped code knows any language. The per-language parsers this design replaced were a catalogue — incomplete by construction, and found reporting their own coverage as complete while blind to ordinary layouts of a language they claimed to parse.

01
Language-agnostic measurement
Config probes, commit conventions, release shape, liveness by directory, and families — the directories that grow by one-more-of-a-kind, whatever the suffix. The scan asks git and nothing else.
02
An extractor written on the spot
The agent, standing in the repository, writes the one function a language appears in. An instruction travels to every language; a catalogue never finishes arriving.
03
Run bounded, believed never
coc_scan.py extract runs it under a deadline, kills whatever it spawned, caps its output, then validates: shape, section caps, every path against HEAD, and files_processed against files_at_head — so an artifact that read a fifth of the repository can never pass as one that read it all.
04
The agent carries the rest
What no extractor states — layering intent, what a chokepoint means, what is enforced by habit — the agent reads, and each becomes a code: observation, held to the same gate and the same path check as every other fact.
The consequence. No language ever has to be added for the pipeline to be complete — there is nothing to add it to. The knowledge lives in the agent's hands at runtime; the shipped code only decides whether what came back can be trusted.
