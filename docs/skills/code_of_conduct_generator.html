code-of-conduct-generator

A Hercules skill that writes a repository's code-of-conduct — the standing document that tells every agent and every contributor how this project is built: its architecture and extension points, its testing bar, its quality gates, and the rules that are never broken. Run it once per repository — "Hercules, set up this project" — and every later session starts pre-calibrated.

It works in three moves: a deterministic tool measures the repository, the skill asks the owner what no scan can answer, and the agent reads the code. Every rule in the document must name evidence from one of those three streams, and programs — not judgment — refuse the draft when it cannot. Nothing is written except the code-of-conduct file itself.

What you get

One file, project-specific, citing real paths. The first sentence of every rule reads alone — that is the line a skimming reader takes away; everything after it is for the reader who stopped.

## Why this is the way it is       ← every reason, last

How it works

Evidence enters by three lanes and leaves as one JSON envelope. Nothing reaches the document that has not passed the envelope gate first.

The workflow

Ten steps. A content test pins the order, so the shipped prose cannot drift out of sequence.

01
Plan, and pick a depth
Nothing is scanned before the user has seen the flow. Quick or Thorough.
02
Find any existing code-of-conduct
One match means update mode, additions-only. Several are never silently resolved — it asks.
03
Scan
Config, history, liveness, and the directories the repo grows by — asked of git, in any language.
3b
Extract the architecture
The agent writes a small extractor for the stack in front of it; the tool runs it under a hard bound and validates every path it reports against the repository.
04
Ask, in one batch
Five or more questions, never trickled. Every split convention found in the code becomes a question — never a majority vote.
05
Draft from all three streams
Every rule cites a fact, an answer, or an observation. No evidence, no rule.
06
Gap pass and critical review
A coverage map finds load-bearing omissions; an advisor reviews the draft. Both recommend — neither silently adds.
07
Gate
Two programs check the draft — evidence, shape, citations, real paths. Exit 0 ships; anything else gets fixed, never argued past.
08
Approve and write
Written atomically, after the user's yes. No other file is created or edited. The linter runs once more, against disk.
09
Commit
Exactly that one path is staged. A push is offered, never taken.

Why the output can be trusted

Not because a model wrote it carefully — because programs refuse it when it is wrong. Every check below exists because that defect really got through once.

01
Every rule is evidenced, or refused
Untagged, uncheckable, or citing evidence the run does not carry — the gate bounces it back with the reason named.
02
Every cited path is real, or refused
Paths resolve against the repository's own file list at HEAD — a claim about a file that does not exist never enters the document.
03
Nothing that rots ships
Snapshot counts, pinned versions, and unverifiable universals ("the only X anywhere") are refused — they are true when written and silently false a week later.
04
The runtime extractor is bounded, never believed
The agent-written extractor runs under a deadline with its output capped, and must report how much of the repository it actually read — a partial read can never pass as a complete one.
05
Universal by design
No shipped code knows any language — the scan asks git, and the language knowledge is written by the agent at runtime, per repository. There is no parser catalogue to fall behind.
Failure is loud. An unreadable repository, a hung extractor, a rule without evidence — each stops the run and names itself. The one thing this pipeline never does is degrade silently into a confident document that covers less than it appears to.
